# 部署、真实接入与数据安全

## 1. 当前实现边界

可本机演示完整链路；云函数提供授权视图、持久化事务及结算入口。当前没有真实支付/退款适配器，生产模式返回 `PAYMENT_NOT_CONFIGURED` / `REFUND_NOT_CONFIGURED`，不会调用模拟流程替代。

没有部署云环境，没有上传或发布微信版本，也没有进行真实微信支付、实际云数据库事务或真机原生渲染验证。云事务测试使用替身验证入口和并发业务语义，不是平台实测。

## 2. 配置清单

| 项目 | 用途 | 当前状态 |

## 3. 云函数试部署

1. 选择微信云开发当前支持且满足项目要求的Node.js运行时（本地验证Node20+，当前机器为Node24）。平台若尚不支持所需运行时，应先验证兼容方案，不强行降级跳过验证。
2. 仓库根目录执行：

   ```sh
   npm ci
   npm run build:cloud
   npm ci --ignore-scripts --prefix cloudfunctions/api
   npm test
   ```

3. `build:cloud` 将共享引擎复制到 `cloudfunctions/api/shared/`，生成无个人资料的 `initial-state.example.json`。每次更新引擎后都重新构建；这两个输出被Git忽略，不是另一套维护源代码。
4. 建立私有集合 `camp_private`，客户端读写权限均为false（见下文）。在控制台导入初始状态示例作为 `_id: state-v1` 的文档，检查期次开营日和规则版本。
5. 初始数据应为 `{ _id: 'state-v1', revision: 0, state: ... }`。文件内无虚构已支付订单；不要把本机演示状态导入生产环境。
6. 设置云函数环境变量，上传部署 `api` 函数与安装依赖，配置管理员身份。不要提供一个普通用户可以自行写入的管理员角色集合。
7. 本机私有配置/工作副本中填写AppID与云环境，将 `miniprogram/config.js` 改为 `mode: 'cloud'`。错误时阻止使用，不会自动转为模拟支付。
8. 云端演示可设置服务端 `APP_MODE=demo`，以真实微信身份创建模拟订单；它仍然是模拟，不扣款。云端不提供本机的角色切换和重置工具。
9. 正式环境应与演示环境独立。设置 `APP_MODE=production` 后，现有模拟订单不会授予生产权限；真实收退款仍被阻止，必须先完成适配器开发和联调。

## 4. 数据与权限

首版试营使用一个仅云函数可访问的状态文档，内部按业务实体分组：

| 实体 | 访问策略 |
| --- | --- |
| users、consents | 本人最小化视图，管理权限来自服务端白名单；健康回答不进入普通成员视图 |
| camps | 对外展示必要期次介绍，付款时保留规则及开营日快照 |
| orders、enrollments | 本人查看，支付状态不能由生产客户端写入 |
| checkins、bodies | 本人记录；管理端按必要范围查看统计，其他成员无权读取 |
| posts、reports | 同营已付费成员可见已审核帖子；待审仅本人及管理员可见 |
| requests | 本人提交及查看，管理员记录处理结果，相关周期暂缓结算 |
| settlements、refunds | 服务端结算，固定原订单周期标识；用户不能直接写入金额 |
| audits | 保留后台操作与导出记录，前端只给管理员最近30条；不会自动删去历史审计 |

在数据库控制台为 `camp_private` 设置客户端安全规则：

```json
{"read": false, "write": false}
```

客户端通过经过微信身份认证的云函数访问。不得为了演示把集合设成公开读写。当前没有启用云图片上传；未来存储权限应隔离用户与期次，并在审核通过后提供授权访问。

每次操作在数据库事务内读取/修改/写回，失败不提交；避免并发结算重复返款，云函数重试不执行外部支付副作用。业务金额为整数分，所有周期预留退款总额上限为实付金额与90000分中的较小值。实际支付适配器实现时须将外部调用放在事务外，通过持久化退款请求、唯一退款单号和查询/通知对账保证幂等。

当前是验证架构，不适合扩大招生直接使用：状态接近800KB时保护性拒绝写入，需要迁移分集合、按订单锁定的事务、索引、权限分层、任务队列及独立审计归档。容量限制不是删除健康或交易记录的授权，不能靠无审计清空数据维持运行。

## 5. 定时任务

当前 `cloudfunctions/api/config.json` 的触发器列表为空，避免部署时未经配置启动任务。

- 完成环境与权限配置后，在云控制台配置平台Timer定期调用 `api`，按平台当前文档设置北京时间周期结束后的执行频率。
- 必须设置 `ENABLE_SCHEDULER=true`。入口要求无普通用户OPENID且为Timer事件；普通客户端伪造 `Type: Timer` 不会取得系统权限。
- 当前定时入口仅结算已结束周期，生成有资格的退款记录。真实退款尚未接入，因此不会实际返款；人工触发结算按钮也不绕过这一限制。
- 本机演示在初始化、管理员结算及推进日期时执行结算；模拟退款需分别点击发起和到账，方便辨认状态。
- 微信订阅提醒和周报推送还需要模板、用户授权、任务与失败处理，目前只有应用内统计，尚无自动推送。

## 6. 支付适配器后续接入要求

- 真实下单服务端校验准入、协议版本、期次、90000分金额，创建商户唯一订单。
- 根据微信平台支持的可信支付通知/查单确认商户、AppID、订单、金额、币种和支付状态，完成验签/解密及防重放后授权，不能相信前端成功回调。
- 每周期退款使用持久化唯一请求标识，先事务预留金额，再调用外部退款；未知结果先查单，不能直接生成新退款编号重试。
- 退款处理中与成功严格区分，处理失败、重复/乱序通知、超时、商户余额不足及跨周期重试。
- 各类退款共同计入原订单上限，退出或取消时考虑已经退回的金额，避免重复退款。
- 沙箱/小额真实联调验证通知、对账、权限及退款后，才允许开放真实收费。当前代码不提供伪造“支付成功”入口作为生产替代。

## 7. 内容、专业审核与运营事项

健康筛查题目、运动饮食模板、营规、暂停/退出/特殊退款规则、健康与隐私告知仍为草稿。上线前由相应医疗/营养与法律专业人员审定，补充运营主体、联系渠道、实际交付内容、处理时限、数据保存期限、备份及删除流程；完成微信隐私保护指引、必要用户授权及平台审核。

目前管理端期次/模板为只读展示；暂停可提交和记录处理结果，尚不自动延期或修改历史记录。需要对外承诺这些能力时，应先实现相应的审计、日期及退款调整规则，不能仅关闭申请就宣称已执行。

所有成员全额取得900元返款时，服务收入全部返出，运营成本另由运营方承担。不得把未经验证的完成率或减重概率写成收益保证；应按承诺的返款上限安排预算与试营人数。
